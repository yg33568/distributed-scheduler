# 01 · 项目功能与具体流程

> 面试前把这份过一遍，能做到"不看代码也能讲清楚每个流程"。
> 所有内容都对应真实代码，可直接对照源码。

---

## 一、项目是什么（一句话）

一个**从零手写**的分布式任务调度系统：调度中心按一致性哈希把分片任务路由到多个执行器，执行器用多级缓存扛热点；调度中心支持 **ZooKeeper 选主的主备高可用集群**，可 **Docker 一键部署**。核心不依赖任何现成调度框架。

## 二、功能清单

| # | 功能 | 一句话说明 | 关键代码 |
|---|---|---|---|
| 1 | 手写 Netty 自定义协议 | 11 字节帧头 + JSON body，处理粘包/半包 | `protocol/Message*` |
| 2 | 一致性哈希分片路由 | MD5 + TreeMap + 150 虚拟节点，节点增减只影响相邻分片 | `ConsistentHashRouter` |
| 3 | 多级缓存 | 布隆→L1 Caffeine→条带锁→L2 Redis→DB，防穿透/击穿/雪崩 | `CacheService` |
| 4 | 分片调度 | leader 每 30s 生成 10 个分片任务下发 | `SchedulerServer.startShardingScheduler` |
| 5 | 任务超时与重试 | 30s 超时 + 最多 3 次重试，重试进队列每 10s 处理 | `dispatchJob` / `retryQueue` |
| 6 | 任务持久化与幂等 | 落 MySQL（task_id 唯一键）；worker 端双集合幂等 | `JobDao` / `ClientHandler` |
| 7 | 故障转移 | worker 下线：任务重放 + 热点 key 按哈希后继迁移 + 重建环 | `doRemoveWorker` |
| 8 | 主备高可用 | 多 master 经 ZK 选主，主挂备切，任务不丢 | `MasterLifecycle` / `JobRecovery` |
| 9 | Worker 自动重连 | ZK 发现 leader，断线指数退避重连，workerId 持久化 | `LeaderDiscovery` / `SchedulerClient` |
| 10 | 管理控制台 | `/status` `/leader` `/workers` `/jobs/pending` | `AdminHandler` |
| 11 | 配置化 | 环境变量 > application.properties > 默认值 | `AppConfig` |
| 12 | Docker 一键部署 | compose 编排 ZK+MySQL+Redis+2主2 worker | `docker-compose.yml` |

## 三、具体流程（重点）

### 流程 1：Worker 注册

```
Worker 启动
  │ resolveWorkerId()：环境变量 WORKER_ID → .worker-id 文件 → 时间戳生成
  ├─ LeaderDiscovery 连 ZK，监听 /scheduler/leader 节点
  ├─ awaitLeader() 拿到 "host:port"
  ├─ Netty connect → 发 register 消息（WorkerInfo{workerId,host,port,healthy}）
  ├─ Leader 收到 register → workers.put(workerId, ctx) → 重建哈希环
  ├─ Leader 回 registerAck（type=102）
  └─ Worker 等到 ACK → 才算注册成功（awaitRegisterAck，10s 超时）
```
**面试点**：为什么要有 registerAck？——注册消息丢了的话，worker 有连接但不在哈希环上，收不到任务也不自知，靠 60s idle 才暴露。ACK 让"注册成功"变成可确认的。

---

### 流程 2：分片调度（leader 每 30s 一次）

```
startShardingScheduler（每30s）
  │ worker 为空 → 跳过
  ├─ for i in 0..9：
  │    jobId = (now<<16) | (salt+i)     ← 实例盐，防同毫秒冲突
  │    taskId = jobId + "_" + i + "_0"
  │    生成 preloadKeys / hotKeys = user:{i*100+0..9}（10个key）
  │    按 taskId 路由 → 把 hotKeys 登记到该 worker 名下（供故障迁移）
  │    dispatchJob(job)
  └─ dispatchJob：
        router.route(taskId) → 目标在线？
          ├─ 是：save DB(PENDING) → 发任务 → pendingJobs.put
          │     → runningTasks[worker].add → 设 30s 超时定时器
          └─ 否：入 retryQueue（等重试调度器）
```
**面试点**：jobId 为什么要 `(now<<16)|salt`？——原实现是 `now + i`，同毫秒两个实例生成会撞 ID；高 16 位放时间、低 16 位放"实例盐+分片号"，同毫秒不冲突，且 task_id 还有 DB 唯一索引兜底。

---

### 流程 3：任务执行 + 幂等（worker 端）

```
收到 TYPE_REQUEST
  ├─ 幂等检查①：taskId ∈ executedTasks（已完成）→ 直接回 success
  ├─ 幂等检查②：taskId ∈ executingTasks（执行中）→ 直接回 success
  │    └─ 防的是：leader 故障重派到同一 worker，避免重复执行/重派死循环
  ├─ 加入 executingTasks
  ├─ execute(job)：
  │    ① prewarm(keys) 预热布隆过滤器
  │    ② 逐个读 10 个 key（缓存加载）
  │    ③ 业务读取（命中 L1）
  ├─ finally 移除 executingTasks
  ├─ 成功 → 加入 executedTasks
  └─ 回 response 给 leader
```
**面试点**：为什么双集合？——`executedTasks` 管"已完事"，`executingTasks` 管"在途"。重派的任务如果已经在执行，直接回成功让 leader 清 pending，任务本来就会完成。

---

### 流程 4：任务超时 / 失败重试

```
超时定时器（dispatchJob 里设的 30s）触发
  ├─ pendingJobs.remove(jobId) 命中 → 说明还没收到结果
  ├─ DB 置 TIMEOUT
  └─ retryCount < 3 → retryCount+1 → 入 retryQueue

startRetryScheduler（每10s取一个）
  └─ dispatchJob(job) → 重新路由/发派/设超时（重试也重新跟踪超时）
```
**面试点**：这个实现修掉了一个经典 bug——旧版重试发送时不重新登记超时/内存状态，任务可能"无人看守"。

---

### 流程 5：Worker 下线故障转移

```
ServerHandler 感知断线（channelInactive / 60s idle / 异常）
  → SchedulerServer.removeWorker(workerId, ctx)
    ├─ 防误删：workers.get(workerId) != ctx → 陈旧连接，忽略
    ├─ ① 任务转移：runningTasks[worker] 里未完成的任务
    │     取消超时 → DB 置 PENDING → 入 retryQueue
    ├─ ② 缓存迁移：先 remove+重建环，再对每个 hotKey
    │     router.route(key) 求"后继节点"，按目标聚合后发 cacheMigrate
    │     （新 worker 收到 → prewarm + 逐个加载）
    └─ ③ 移除节点：重建哈希环，后续任务不再发给它
```
**面试点**：迁移目标为什么不能随便选？——缓存迁移是为了"新节点的缓存不是冷的"，应该迁到**哈希环上该 key 的正确后继者**（将来这个 key 的读请求会打到它），而不是 `iterator().next()` 随便一个。

---

### 流程 6：Master 主备切换（核心卖点）

```
正常时：
  master-a 成为 leader（LeaderLatch）
    ├─ startTcpServer（绑定 8080，收 worker 连接）
    ├─ startSchedulers（分片/重试调度）
    ├─ JobRecovery（从 DB 恢复任务）
    └─ 写 ZK 临时节点 /scheduler/leader = "scheduler-a:8080"
  master-b standby：不绑 TCP，只跑 Admin

leader 挂了（kill scheduler-a 容器）：
  ① ZK 会话超时 → /scheduler/leader-latch 选举触发
  ② master-b 的 LeaderLatch isLeader 回调 → becomeLeader()
  ③ master-b 启动 TCP → worker 发现断线 → 重连 master-b → 重新注册 → 重建哈希环
  ④ master-b JobRecovery：findPendingJobs()（DB 里 PENDING/RUNNING）
     → 重置 retryCount → dispatchJob 重派
     → worker 幂等兜底，已完成的直接回 success
  ⑤ 被降级的旧 leader 如果还活着：notLeader → shutdown() 停调度防脑裂
```
**面试点**：
- 为什么不双活？——单 leader 调度逻辑简单、无分布式锁开销；双活要解决"两个 leader 同时派同一任务"的一致性。主备是更稳妥的取舍。
- 任务会不会丢？——不会丢（at-least-once），但可能重复执行，靠 worker 幂等兜底。
- 脑裂怎么办？——单 ZK 无法严格仲裁，极端分区下可能短暂双 leader，靠幂等兜底为 at-least-once。生产要 3 节点 ZK + fencing。

---

### 流程 7：缓存读取（多级）

```
get(key)：
  ① 布隆过滤器（已预热且 mightContain=false）→ 直接 null（防穿透，不打后面层）
  ② L1 Caffeine → 命中返回（含 NULL 标记短路）
  ③ Striped 条带锁（防击穿：同一 key 只有一个线程进临界区）
     double-check L1
  ④ L2 Redis → 命中回填 L1
     （Redis 挂了 → 降级到 DB，不阻断读）
  ⑤ DB(DataLoader) → 命中：写 Redis(随机TTL防雪崩) + 写 L1 + bloomFilter.put
     → 未命中：写 NULL 空值缓存(60s, 防穿透)
```
**面试点**：
- 布隆过滤器为什么必须预热？——它是"已知存在集合"的门禁，不预热会把真实 key 误杀成"不存在"。生产从数据集批量灌入。
- 防雪崩怎么做的？——DB 回填 Redis 时 TTL = 300 + random(0~60)s，避免同一时刻集体过期。
- Striped 锁 vs 手写 per-key map？——per-key map + `unlock 后 remove` 有竞态（A 解锁移除后 C 建新锁，与排队中的 B 同时进临界区）；固定条带锁无 map 无竞态。

---

### 流程 8：缓存迁移（故障时）

```
Leader 在 removeWorker 里：
  ├─ 对每个 hotKey：router.route(key) → 后继 worker
  ├─ 按后继聚合：{worker-x: [key1,key3...], worker-y: [key2...]}
  ├─ 对每个目标发 cacheMigrate 消息（含 hotKeys 列表）
  └─ 新 worker：prewarm(hotKeys) → 逐个 get 加载到 L1/L2
```
