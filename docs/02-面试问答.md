## 一、项目介绍（开场 2 分钟版）

**Q：简单介绍一下你的项目？**

> 这是一个分布式任务调度系统。调度中心用 Netty 自定义 TCP 协议和多个执行器通信，通过一致性哈希把分片任务路由到对应执行器；执行器用"布隆过滤器 + Caffeine 本地缓存 + Redis + 数据库"的多级缓存来扛热点。关键点是**高可用**：调度中心支持多实例集群，用 ZooKeeper 做主备选举，leader 挂了备机自动接管，任务从数据库恢复、不丢失。整套系统用 Docker Compose 一键部署，我在里面手写了协议、一致性哈希、选主、故障恢复这些核心机制，没有依赖现成的调度框架。

**Q：为什么选这个项目？解决什么问题？**

> 我观察到很多真实场景（比如 XXL-Job、ElasticJob）的任务调度，核心就两件事：**任务怎么分**、**任务怎么不丢**。我想自己从头把这两件事做一遍，顺便把多级缓存、一致性哈希、分布式选主这些"八股"真正落到代码里。项目解决的核心问题是：单机调度中心是单点故障，我通过 ZK 选举 + 数据库恢复解决了"调度中心挂了任务不丢"。

## 二、架构设计

**Q：整体的架构是怎样的？画一下。**

> 三个模块：scheduler-common（协议+配置+ZK 工具）、scheduler-core（调度中心）、scheduler-worker（执行器）。调度中心集群通过 ZK 选出一个 leader，只有 leader 起 TCP 服务和调度器；worker 通过 ZK 服务发现找到当前 leader，TCP 长连接注册。leader 每 30 秒生成 10 个分片任务，用一致性哈希路由到 worker；worker 执行完把结果回给 leader。任务全程落库（MySQL），所以 leader 挂了新 leader 能恢复。

**Q：为什么拆成三个模块？**

> common 是公共能力（协议编解码、消息对象、配置、ZK 客户端工厂），core 和 worker 都依赖它；core 管调度、worker 管执行。这样 worker 可以单独横向扩展，协议层复用，也方便以后接新的执行器类型。

## 三、Netty 自定义协议 ⭐

**Q：为什么自定义协议，不用现成的比如 HTTP 或 Protobuf？**

> 三个原因：① 场景是调度中心↔worker 的高频长连接，自定义 TCP 帧比 HTTP 更轻量（帧头 11 字节，无 HTTP 头开销）；② 我想展示对网络底层的理解——粘包、半包、魔数、编解码都是自己处理；③ 协议简单可控，消息类型就 request/response/heartbeat/register/cacheMigrate/registerAck 六种，JSON body 足够。

**Q：你的协议帧结构是什么样的？**

> 固定 11 字节帧头：魔数(4) + 版本(1) + 消息类型(1) + 状态(1) + 长度(4)，后面跟 JSON body。魔数是 0xCAFEBABE，解码器先读魔数，不对就直接关连接，快速识别非法数据。

**Q：粘包和半包怎么处理的？**

> 粘包（一次收多个消息）：解码器循环读，每次按"长度字段"切出完整的帧。半包（一个消息分几次到）：先 `markReaderIndex` 标记位置，读头部发现 body 不够时 `resetReaderIndex` 回滚，等下一次数据到达再继续。这是 Netty `ByteToMessageDecoder` 的经典做法。我写了单元测试覆盖三种情况：正常、两包连发、半包分次到达。

**Q：body 用什么序列化？为什么不用 JDK 序列化？**

> JSON（Jackson）。JDK 序列化有安全漏洞（反序列化攻击）、体积大、跨语言差；JSON 体积小、可读、worker 换成别的语言也能接。项目里任务上下文、执行结果都是 JSON 传输。

**Q：为什么需要心跳？**

> 长连接要探测对端是否还活着。worker 每 30 秒发心跳；调度中心侧配了 `IdleStateHandler` 60 秒没读到数据就判定 worker 失联，触发故障转移（任务重放+缓存迁移+移除节点）。心跳也防止连接被中间设备空闲断开。

## 四、一致性哈希 ⭐

**Q：一致性哈希原理？为什么用 150 个虚拟节点？**

> 把节点哈希到 0~2³²-1 的环上，key 哈希后顺时针找第一个节点。**虚拟节点**是把每个真实节点复制成 N 个虚拟节点均匀撒在环上，解决真实节点少时数据倾斜的问题（比如 3 个节点，直接哈希可能某个节点负载 60%）。150 个是我在平衡"分布均匀度"和"内存/重建开销"选的：虚拟节点太少倾斜明显，太多每个节点要存 150 个哈希值、节点增删重建成本高。实际我单元测试验证过 150 个时 300 个 key 能均匀落在 3 个节点上。

**Q：节点增减会发生什么？为什么只有部分数据受影响？**

> 用 TreeMap 存哈希环，`tailMap(key)` 找后继。增删节点只会影响该节点在环上"逆时针到上一个节点"这一段的 key，其他 key 路由不变。我写的测试验证了：移除一个节点后，原本属于它的 key 全部被它的**后继节点**接管，而不是乱跳。

**Q：为什么选择 TreeMap？**

> TreeMap 按 key 有序，`tailMap(hash)` 一次就能找到大于等于该哈希的最小节点，O(logN)；比手写循环找最小更简单可靠。

## 五、多级缓存 ⭐

**Q：多级缓存分几层？为什么分这么多层？**

> 5 层：布隆过滤器 → Caffeine L1（本机内存）→ 条带锁 → Redis L2 → 数据库。每一层解决一个问题：布隆过滤器把"肯定不存在"的 key 挡在最前面（防穿透）；L1 本机内存最快，扛住热点；Redis 是跨 worker 共享的第二级；数据库是最后兜底。缓存的思想是"越近越快，越远越全"。

**Q：怎么防穿透？**

> 两个手段：① **布隆过滤器**——把数据集中已知存在的 key 灌进过滤器，查询先过过滤器，`mightContain=false` 说明 key 肯定不存在，直接返回，不往下打；② **空值缓存**——如果真的查到 DB 也没有，把这个 key 的"NULL 标记"缓存 60 秒，短时间内的重复查询直接命中空值，不再打库。

**Q：布隆过滤器有什么坑？**

> 布隆过滤器只有"可能包含"和"肯定不包含"，**有误判率（false positive）但没有 false negative**。关键坑是：它必须是"已知存在集合"，**必须预热**。我最初实现有个 bug——过滤器只在"DB 查到数据"时才 put，导致第一次查询任何 key 都被过滤器挡掉，整个缓存失效。后来加了 `prewarm()` 方法，worker 在分片预热/缓存迁移时批量灌入。生产环境要从数据集或键注册表批量初始化。

**Q：怎么防击穿（缓存失效瞬间大量请求打 DB）？**

> 互斥锁 + double-check。同一时间只有一个线程进临界区去查 Redis/DB，其他线程在锁上等待，第一个查完回填缓存后，后面的线程 double-check 命中缓存直接返回。我用的是 Guava `Striped.lazyWeakLock(1024)` 固定条带锁。

**Q：为什么用 Striped 锁，不用 Map<key, Lock>？**

> 手写 per-key map 有个经典竞态：`lock.unlock()` 之后 `map.remove(key)`，这时候如果另一个线程刚 `computeIfAbsent` 拿到这把锁在排队，第三个线程又 `computeIfAbsent` 建了一把**新锁**进临界区，两个线程同时打 DB，防击穿失效。Striped 是按 key 哈希取固定条带，没有 map 没有 remove 竞态，还不会无限增长。

**Q：怎么防雪崩？**

> DB 回填 Redis 时，过期时间 = 基础 300 秒 + 0~60 秒随机数，避免大量 key 同一时刻集体过期，形成对 DB 的瞬时压力。

**Q：Redis 挂了怎么办？**

> 封装了 `getFromRedis`/`writeToRedis`，异常捕获降级到下一层（DB），不阻断读取，只打 warn 日志。缓存的设计原则是"缓存可以失效，不能把服务打挂"。

**Q：缓存一致性怎么保证？（可能问）**

> 目前 worker 之间通过"故障时的热点 key 迁移"来预热，还有一张 `CacheMessage`（EVICT/UPDATE）广播协议预留了但没接线。真正的强一致需要写请求穿透到所有 worker 逐出本地缓存，或者用版本号/失效通知，这是我在 README 里诚实标注的已知限制和下一步扩展点。面试可以答：这里我选择了"最终一致 + 短 TTL"，因为任务场景对秒级不一致可容忍。

## 六、主备高可用 / ZooKeeper ⭐

**Q：为什么选 ZooKeeper？**

> 两个能力：① **Leader 选举**——`LeaderLatch` 在 `/scheduler/leader-latch` 上竞争，只有 leader 调度，天然避免"双 leader 同时派任务"；② **服务发现**——leader 把地址写进 `/scheduler/leader` 临时节点，worker 监听这个节点，leader 换了 worker 自动知道新地址。ZK 的**临时节点**会随会话失效自动删除，所以 leader 挂了节点自动消失，选举自动触发，不需要额外的"死亡检测"。

**Q：LeaderLatch 的原理？**

> 多个客户端竞争同一个 path，按 ZK 的顺序临时节点，序号最小的成为 leader；leader 的会话没了（挂/网络断超时），节点消失，下一个接任。Curator 把这一套封装成 `LeaderLatch`，注册 `LeaderLatchListener` 监听 `isLeader`/`notLeader` 回调。

**Q：主备模式 vs 双活？为什么选主备？**

> 主备（Active-Standby）：同一时刻只有一个 leader 调度，逻辑简单，没有分布式锁、没有任务冲突，切换时新 leader 从 DB 恢复。代价是备机资源闲置、调度吞吐没水平扩展。双活（Active-Active）：多个 master 同时调度，要解决"两个 leader 同时派同一任务"的一致性问题，需要分布式锁或幂等更强的手段，复杂度高。我选主备是因为它把"高可用"这个目标用最简单可靠的方式达成了，作为练手项目更稳妥。

**Q：leader 挂了，任务会不会丢？**

> 不会丢，是 **at-least-once**。所有任务派发前先落 MySQL（状态 PENDING），新 leader 接管时 `findPendingJobs()` 把 PENDING/RUNNING 的任务捞出来重新派发。但可能**重复执行**：比如任务已经发给 worker 在跑、leader 挂了，新 leader 重新派，worker 端幂等兜底（已完成/执行中的 taskId 直接回成功）。所以语义是"至少一次，绝不丢失，可能重复"，对幂等任务无害。

**Q：幂等具体怎么做？**

> 双层：① 数据库 `task_id` 唯一索引，重复插入会被拦；② worker 端两个内存集合——`executedTasks`（已完成）和 `executingTasks`（执行中）。收到任务先查这两集合：已完成直接回成功，执行中直接回成功（防重派死循环），否则才真正执行。注意 worker 重启会丢内存幂等集，这是 at-least-once 的来源。

**Q：脑裂怎么处理？**

> 这是分布式系统经典问题。单 ZK 节点无法严格仲裁（没有 quorum），极端网络分区下可能短暂出现两个 leader 都在调度。我的处理：① 被降级的节点 LeaderLatch 触发 `notLeader` 就调用 `shutdown()` 停掉调度器和 TCP，尽量缩短"旧 leader 还在调度"的窗口；② worker 幂等兜底，双 leader 重复派发的任务在 worker 端被去重。README 里诚实说明：生产环境需要 3 节点 ZK ensemble 做仲裁 + 数据层 fencing token。面试官问这个，重点在于你**知道**局限，而不是说"我完美解决了"。

**Q：ZK 客户端用的什么？为什么？**

> Apache Curator。它是 ZK 官方推荐的 Java 客户端，`LeaderLatch`、`PathChildrenCache`（监听子节点变化）都是现成的 recipe，比裸 ZK API 写选举/监听可靠得多。

**Q：worker 怎么发现新的 leader？（服务发现）**

> worker 启动时用 `PathChildrenCache` 监听 `/scheduler` 下的 `leader` 子节点。leader 把地址写进这个节点（临时节点，数据是 "host:port"）。leader 一换，事件触发，worker 拿到新地址 → 断线重连 → 重新注册。所以 worker 不需要写死任何一个 master 的地址。

## 七、分布式基础概念

**Q：at-least-once、at-most-once、exactly-once 怎么理解？你的系统是哪种？**

> 我的系统是 at-least-once：任务至少执行一次，不丢，可能重复。原因是 leader 故障恢复靠 DB 重放，而 worker 幂等集在内存，重启会丢。要做到 exactly-once 要么把幂等状态持久化（Redis/DB 记录 taskId），要么任务本身幂等。面试可以补充：绝大多数调度系统都是 at-least-once + 任务幂等，这是工程上的现实选择。

**Q：分布式锁你了解吗？和 Leader 选举的区别？**

> 分布式锁解决"多个进程互斥访问某个资源"；Leader 选举本质是一种分布式锁的变体（锁住"谁是 leader"）。可以用 ZK 临时节点或 Redis SETNX 实现。我这个项目里，主备选举就相当于给"调度权"加了一把分布式锁。

**Q：CAP 理论和你项目的关系？**

> 调度中心在选主时更偏向 **CP**（一致性优先：同一时刻只有一个 leader），用 ZK 保证"选举结果一致"；任务状态持久化在 MySQL，也是 CP。缓存这一侧更偏向 **AP**（可用性优先：Redis 挂了降级到 DB，接受短暂不一致）。分布式系统里不同组件可以有不同的取舍。

## 八、性能与并发

**Q：用了哪些并发手段？**

> ① 注册表、pending、running 都用 `ConcurrentHashMap`；② 重试队列用 `ConcurrentLinkedQueue`；③ 超时定时器用单线程 `ScheduledExecutorService`（单线程避免多线程并发改 pendingJobs 的竞态）；④ worker 幂等集合用 `newKeySet()`（CopyOnWriteArraySet 的并发版）；⑤ 防击穿用 Striped 锁。

**Q：超时是怎么实现的？会不会泄漏？**

> 每个任务派发时 `timeoutExecutor.schedule()` 设一个 30 秒的定时任务，任务完成或 worker 下线时把对应的 `ScheduledFuture` cancel 掉。用 `ConcurrentHashMap<jobId, ScheduledFuture>` 关联。任务正常完成→取消定时器；定时器先触发（超时）→ 从 pending 移除并入重试队列。

**Q：如果 worker 处理慢，任务堆积怎么办？（可扩展）**

> 目前是固定每 30 秒 10 个分片、每个分片 10 个 key，worker 端同步 `Thread.sleep(500)` 模拟执行。真实场景会有线程池限流、背压、任务队列上限。这是我标注的扩展点，可以答"下一步会加动态线程池和限流"。

## 九、数据库与持久化

**Q：为什么任务要落库？落什么？**

> 为了 leader 故障恢复。任务派发前写进 `schedule_job`（job_id、task_id、job_name、params、分片信息、目标 worker、状态、重试次数）。`task_id` 有唯一索引做幂等。状态流转：PENDING →（执行中）RUNNING → SUCCESS / FAILED / TIMEOUT。

**Q：连接池用的什么？怎么处理 DB 没就绪？**

> HikariCP（性能最好的 Java 连接池）。设了 `initializationFailTimeout=-1`，这样容器启动时 MySQL 还没起来不会导致 JVM 崩，首次访问时连接池再重试（`connectionTimeout=5000`）。

## 十、部署与运维

**Q：怎么部署的？**

> Docker Compose 一键：zookeeper、mysql、redis 三个基础服务 + scheduler-a/b 两个调度中心（主备）+ worker-a/b 两个执行器。调度中心是多阶段 Dockerfile（maven 构建打 fat-jar → JRE 运行），全部配置通过环境变量注入，不硬编码。

**Q：配置是怎么管理的？**

> 三级：环境变量 > application.properties > 代码默认值。用统一的 `AppConfig.get()` 封装。这样本地直接跑用 properties 里的默认值，容器里用环境变量覆盖（比如 `DB_JDBC_URL=jdbc:mysql://mysql:3306/...`）。这是很实际的经验：一套代码两种跑法。

**Q：你怎么验证系统是好的？（测试）**

> 单元测试 12 个全绿：协议编解码（正常/粘包/半包/新类型）、一致性哈希（路由确定性/分布均衡/节点移除后继接管/新增负载迁移）、配置中心。端到端用 Docker 演示：起 2 主 2 worker → curl `/status` 看主备 → 杀 leader 看备机接管、worker 重连、任务恢复。

## 十二、可能会被追着问的细节

**Q：`System.currentTimeMillis() + i` 当 jobId 有什么问题？**

> 同毫秒内两次调度会生成相同 jobId，如果两个 master 并发就更明显。改成 `(now << 16) | (salt + i)`：高 16 位是时间，低 16 位是"实例随机盐+分片号"，同毫秒不冲突；DB 还有 task_id 唯一索引兜底。

**Q：`removeWorker` 里为什么要把节点先移除再迁移？**

> 缓存迁移要算"这个 key 该归谁"，必须先基于**移除后的哈希环**来路由，得到正确的后继节点。如果还在旧环上算，会算到已经下线的 worker 自己头上。

**Q：为什么用 `executingTasks` 而不是直接在 worker 侧加锁？**

> 因为问题不是"同时执行同一任务"（worker 是单线程按消息顺序处理），而是"leader 故障重派导致重复派发"。`executingTasks` 是给 leader 的"我在忙这个任务"的信号，让重派直接拿到成功结果，避免误判超时。

**Q：worker 重连时心跳线程怎么办？**

> 心跳线程是**一条**守护线程，跨重连复用，每次从 `channel` 字段拿当前连接判断 `isActive`。这样不会每次重连都泄漏一个线程。发送前还 try-catch，连接断了直接跳过。
