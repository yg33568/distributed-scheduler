## 标准版演示（10 分钟）

### 第 0 步 · 开场白（1 分钟）

> 这是我手写的分布式任务调度系统，没有用 XXL-Job 这类现成框架。三个模块：common 是协议，core 是调度中心，worker 是执行器。调度中心是**多实例主备**，靠 ZooKeeper 选主；worker 靠 ZK 发现 leader，TCP 长连接注册。现在环境里起了 2 个调度中心、2 个 worker，加上 ZK/MySQL/Redis。

**讲解动作**：打开 `docker compose ps`，指着跑起来的容器。

---

### 第 1 步 · 验证主备（1 分钟）

```bash
curl localhost:18081/status    # scheduler-a
curl localhost:18082/status    # scheduler-b
```

**预期输出**：
```
# 18081 → scheduler-a（当前 leader）
{"role":"LEADER","isLeader":true,"port":8080,"leader":"scheduler-a:8080",
 "workers":["worker-a","worker-b"],"pendingJobs":0}
# 18082 → scheduler-b（standby）
{"role":"STANDBY","isLeader":false,"port":8080,"leader":"scheduler-a:8080","workers":[],"pendingJobs":0}
```

**要说的话**：
> 关键在 `leader` 字段——这个地址是 scheduler-a 通过 ZK 写进 `/scheduler/leader` 临时节点的，worker 就是靠监听这个节点做服务发现，所以**任何一台 master 挂了，worker 都能自动找到下一个**。

---

### 第 2 步 · 观察分片调度（2 分钟）

```bash
curl localhost:18081/jobs/pending          # 任务数应增长（每30s一批）
curl localhost:18081/workers               # 应看到两个 worker
docker compose logs -f scheduler-a | grep Sharding   # 看路由日志
```

**预期日志**：
```
[Sharding] Start, total shards: 10
[Dispatch] Job 172xxx (shard=0) -> worker-a
[Dispatch] Job 172xxx (shard=1) -> worker-b
...
```

**要说的话**：
> leader 每 30 秒生成 10 个分片任务，每个任务用一致性哈希按 taskId 路由到 worker。**这里我要强调**：任务在发给 worker 之前已经落 MySQL 了，状态 PENDING——这就是后面故障恢复的基础，任务永远不丢。
> worker 那边每个分片会预热 10 个 key 到多级缓存，可以切到 worker 日志看缓存命中。

```bash
docker compose logs -f worker-a | grep -E "Preload|L1 hit|Bloom"
```

---

### 第 3 步 · 演示 Worker 故障转移（2 分钟）

```bash
docker compose stop worker-a
docker compose logs -f scheduler-a | grep -E "Re-queued|Migration"
```

**预期日志**：
```
Re-queued task 172xxx from failed worker worker-a    # 任务转移，不丢
[Migration] Migrated 10 keys from worker-a to worker-b   # 热点key按哈希后继迁移
Worker removed: worker-a, remaining workers: 1
```

**要说的话**：
> worker 下线，调度中心做三件事：**任务转移**——把 worker-a 没做完的任务放回重试队列，每 10 秒重新派发；**缓存迁移**——worker-a 的热点 key 不是随便发给谁，而是按一致性哈希算出**正确后继节点** worker-b，这样 worker-b 的缓存不是冷的；**移除节点**——重建哈希环，后续任务不再发给它。

```bash
docker compose start worker-a     # 恢复
```

---

### 第 4 步 · 演示 Master 主备切换（核心，3 分钟）

```bash
# 杀掉当前 leader（scheduler-a）
docker compose stop scheduler-a

# 观察 scheduler-b 接管
docker compose logs -f scheduler-b | grep -E "BECAME|Recovery|Dispatch"
docker compose logs -f worker-a | grep -E "Leader"
```

**预期日志**：
```
# scheduler-b：
>>>> BECAME LEADER (scheduler-b:8080)
[Recovery] Reloaded 5 pending/running jobs from DB, 5 dispatched
[Dispatch] Job 172xxx -> worker-b
# worker：
Leader discovered: scheduler-b:8080
```

**验证**：
```bash
curl localhost:18082/status      # isLeader 变 true，workers 恢复 [worker-a, worker-b]
```

**要说的话**：
> 我把调度中心整个杀掉。ZK 会话超时触发选举，scheduler-b 接任，干了三件事：起 TCP 服务接收 worker；**从数据库恢复任务**——把 PENDING/RUNNING 的捞出来重新派发；写新的 leader 节点。worker 检测到断线，从 ZK 读到新地址重连。任务一条没丢。
> **注意这里 worker 端有幂等**：如果恢复的任务之前已经在 worker 上跑过，worker 的 `executedTasks`/`executingTasks` 会直接回"成功"，不会重复执行。

```bash
docker compose start scheduler-a   # 回来当 standby
curl localhost:18081/status        # 变 STANDBY
```

### 第 5 步 · 收尾总结（1 分钟）

> 这个项目我重点展示了三块：**手写协议和一致性哈希**（底层）、**多级缓存抗热点**（性能）、**ZK 主备 + 数据库恢复**（高可用）。局限我也清楚：单 ZK 无法严格仲裁脑裂，生产要 3 节点 ensemble；worker 幂等集在内存，重启会退化为 at-least-once。这些问题下一步怎么解决我也有方案。

## 代码讲解版（5 分钟，对着源码走查）

**1. 协议 — `scheduler-common/protocol/`（1 分钟）**
> `MessageDecoder`：先 `markReaderIndex`，读 11 字节帧头拿 body 长度，不够就 `resetReaderIndex` 等下一包——这就是粘包/半包处理。魔数不对直接关连接。协议只有 6 种消息类型，register 之后 master 回 registerAck，worker 拿到 ACK 才确认注册成功。

**2. 一致性哈希 — `ConsistentHashRouter`（1 分钟）**
> MD5 哈希 + TreeMap 环 + 150 虚拟节点。`tailMap` 找后继。增删节点只影响相邻一段。单元测试验证了"移除节点后 key 被正确后继接管"。

**3. 多级缓存 — `CacheService`（1 分钟）**
> 布隆(防穿透) → L1 Caffeine → Striped 条带锁(防击穿) → Redis(防雪崩=随机TTL) → DB。Redis 故障降级。这里有个我踩过的坑：布隆过滤器必须 `prewarm`，否则会把所有真实 key 误杀。

**4. 高可用 — `MasterLifecycle` + `JobRecovery`（1 分钟）**
> `LeaderLatch` 选主；leader 把地址写 `/scheduler/leader` 临时节点。`JobRecovery` 从 DB 重放 PENDING/RUNNING。被降级节点 `shutdown()` 防脑裂。

**5. Worker HA — `LeaderDiscovery` + `SchedulerClient`（1 分钟）**
> `PathChildrenCache` 监听 leader 节点，断线后指数退避重连。workerId 持久化保证哈希亲和。

## 面试官追问应对表（速记）

| 面试官问 | 你的落点 |
|---|---|
| 为什么不用 XXL-Job？ | 想展示底层能力，手写协议/一致性哈希/选主；且可控可讲 |
| 主备为什么不用双活？ | 单 leader 逻辑简单无锁开销；双活要解决重复派发一致性 |
| 任务会丢吗？ | at-least-once：先落库再派发，leader 挂了 DB 重放；可能重复但 worker 幂等 |
| 脑裂？ | 单 ZK 无法仲裁，靠 shutdown 缩短窗口 + worker 幂等兜底；生产要 ensemble+fencing |
| 布隆过滤器误判？ | 只有误报没有漏报，误报走 NULL 空值缓存短路，代价是一次多余查询 |
| 缓存一致性？ | 任务场景对秒级不一致容忍，最终一致 + 短 TTL；CacheMessage 广播是扩展点 |
| 怎么横向扩展？ | worker 直接加实例（ZK 注册）；master 目前主备，双活是扩展方向 |
| 最难的 Bug？ | 布隆过滤器空转、Striped 锁竞态、重试不跟踪超时——讲清楚问题和怎么定位 |
